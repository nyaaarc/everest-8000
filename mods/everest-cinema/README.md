# Cinema: a scriptable camera, character director and frame-stepped recorder for Minecraft (Fabric 1.21.1)

A client mod plus a Python client. Through a strict, typed JSON-RPC 2.0 API on `127.0.0.1` it can:

- fly a detached cinematic camera along keyframe splines, orbits, dollies, trucks and follow moves (roll and FOV included);
- direct **actors**: client-side player clones with any skin, an outfit, a held item and a dyed pack, plus the real
  player. They walk routes found over the blocks with vanilla physics, steer like a person, slow down on climbs, stop
  for breathers, look around, and act (swing, draw a bow, raise a radio, crouch into the wind, climb ladders) on per-actor
  timelines;
- puppet the local player directly (walk a path with real physics, look, sneak, jump, hold input, equip items);
- run commands and return their feedback, set time and weather;
- wait until the world is **fully drawn** before a take (chunks, Distant Horizons LODs, and a stable picture);
- record deterministic video. Each rendered frame advances the game clock by exactly 1/fps, so output is smooth however
  slowly the game renders with shaders and Distant Horizons.

Shots are JSON specs validated against the published schemas in `schema/`, so whole sequences can be generated by code and
rendered in batch. Nothing in the mod is specific to one world (the outfit hooks for Everest Expedition and Traveler's
Backpack are optional). `examples/` has worked examples.

## Install and run

1. Build: `JAVA_HOME=<jdk 25> gradle build` produces `build/libs/everest-cinema-<ver>.jar` (Loom 1.18.4, Mojang mappings)
   and runs the unit tests. Put the jar in a client instance's `mods/` with Fabric API.
2. The mod is inert unless `config/everest-cinema.json` says otherwise:
   `{"enabled": true, "port": 25580, "token": "<random>", "ffmpeg": "ffmpeg"}`.
   `tools/launch_game.sh` writes this file with a fresh token on every launch.
3. ffmpeg must be on PATH, or set its full path in `ffmpeg`. NVENC codecs need an NVIDIA GPU.

Run everything headless with one command:

```
tools/render_shots.sh shots.json [out-dir] [--shots a,b] [--preview] [--stills N]
```

It validates the file, launches the Prism instance (`CINEMA_INSTANCE`, default "Everest Cinema"), waits for the world,
snapshots the game state, and runs the file's `setup` actions. Then it renders every shot (or only those named by
`--shots`) to `<name>.mp4` with a `<name>_sheet.png` contact sheet and a `<name>.json` report. Finally it runs `teardown`,
restores the snapshot, quits the game, and writes `summary.json`.

With `--preview`, each shot plays at half size and 20 fps instead, and the run writes evenly spaced stills plus the
contact sheet so the framing can be checked first. Optional `CINEMA_PRE_HOOK` and `CINEMA_POST_HOOK` commands run before
launch and after exit; the Everest wrapper `tools/render_shots.sh` uses them to guard and restore player files.

To drive a running game interactively, use `client/cinema.py`:

```python
import sys; sys.path.insert(0, r"...\everest-cinema\client")
from cinema import *
c = Cinema.from_instance(r"C:\Users\me\AppData\Roaming\PrismLauncher\instances\Everest Cinema")
c.wait_ready()                       # API up and player in a world
c.snapshot()                         # restore point
s = shot("summit_orbit", 8,
         orbit(point(20706.5, 2032, 7774.5), radius=170, height=30, start_deg=250, end_deg=285, fov=50,
               easing="sineInOut"),
         player={"visible": False, "ride": True},
         setup=[a_time(12250), a_command("weather clear")])
validate(s, "shot.schema.json")      # offline check against the published schema
print(c.render(s, r"D:\renders", render=render_settings(2560, 1440, 60), preview=preview_settings(0.5, 4)))
c.restore()
```

## Conventions

- Positions are `[x, y, z]` in blocks, and times are in seconds.
- Yaw and pitch follow Minecraft: yaw 0 faces south (+Z), 90 faces west, 180 north, -90 east; positive pitch looks down.
- An azimuth (`orbit.startDeg`, `dolly.azimuthDeg`, `truck.azimuthDeg`) is the bearing from the target to the camera,
  written as a yaw. With azimuth 0 the camera is south of the target, looking north.
- `fov` is the vertical field of view in degrees.
- Positive `roll` banks the camera to the left, so the horizon turns clockwise.
- The frame size is `render.width`/`height`, 16:9 by default (2560x1440; 3840x2160 for 4K). Other aspect ratios work the
  same way, for example 2560x1072 for 2.39:1. Since `fov` is vertical, a wider frame shows more to the sides at the same
  `fov`; to keep a 2.39 composition's width in 16:9, raise the fov so `tan(fov/2)` grows by 2.39/1.778.
- The window takes the frame size when the screen can hold it. Otherwise (`render.offscreen` `auto`, the default) the
  game renders offscreen at the full size: the framebuffer, Iris's and Distant Horizons' buffers and the GUI layout are
  all built for it, and the window shows the frame scaled down. `state.get.window.offscreen` says which.

## Frame-stepped capture

While recording, the mod wraps the game clock (`Util.timeSource`; it re-installs the wrapper every frame because
Minecraft replaces the time source during start-up). Every frame starts at `start + n/fps`, then the game ticks and
renders, and the finished frame (GUI included, so HUD shots work) is read back from the main render target. The raw BGRA
frame streams into ffmpeg's stdin on a writer thread.

The clock drives everything that animates in client time: ticks, entity interpolation, Iris's `frameTimeCounter` (read
through `Util.getNanos`), shader clouds tied to world time, weather particles and HUD animations. All of it plays at true
speed in the output.

Server-side motion still runs in real time, which covers mobs and server weather transitions. `render.serverTickSync`
lowers the server's tick rate to match the render speed, and client ticks are compensated. The reverse trick also works:
raise `tick rate` in an event to make a slow server-side process, such as a storm building, happen faster in the video.

### Riding, and the sky flicker it used to cause

With `player.ride` the (spectator) player travels with the camera so chunks load around it. The rider is placed on
**every frame**, along the camera's own path, with its previous-position fields set too so nothing interpolates. A jump
of more than 8 blocks (a cut, or the start of a take) goes through the server's `/tp` and waits for arrival.

Earlier versions moved the rider once per tick in big steps. The server rejected those moves ("moved too quickly") and
snapped the player back every tick, so the sky, fog and clouds, which are drawn relative to the player, changed on the
one frame in three where a tick ran. That shows as a 20 Hz pulse in the sky band: a ratio of 3.7-11 against frame noise
in every riding shot of the old trailer, against 0.1-0.8 in shots that didn't ride.

The mod now counts server position corrections (`world.lodStatus.serverPositionCorrections`), and a render warns
if any happened during the roll. `tools/sky_check.py` is the regression check (see Tools).

## Shot spec (`schema/shot.schema.json`)

```jsonc
{
  "name": "storm_summit",                 // [A-Za-z0-9_.-]{1,64}, also the output file name
  "durationSec": 9,
  "camera": { "type": "orbit", ... },      // a Move, see below
  "player": {                             // optional
    "visible": false,                     // render the player model (default: true unless riding)
    "ride": true,                         // move the (spectator) player with the camera so chunks load around it
    "gamemode": "spectator",              // set before warm-up
    "pos": [x, y, z], "yaw": 0, "pitch": 0  // teleport before warm-up
  },
  "hud": {"visible": false, "chat": false, "crosshair": false, "hand": true},   // optional, default hidden
  "shaders": true,                        // optional: switch Iris shaders for this shot
  "setup": [Action...],                   // run in order before warm-up; may wait
  "actors": [Actor...],                   // spawned before warm-up; timelines start on the take's first frame
  "keepActors": false,                    // leave them in the world after the take (default: despawn)
  "warmup": {"lod": LodGate, "minSec": 1, "scout": false, "scoutSpeed": 1,
             "chunksTimeoutSec": 45, "lodSettleSec": 4},   // the last two only when lod.enabled is false
  "events": [{"atSec": 0.5, "action": Action}],   // fired at shot time; no waiting actions
  "teardown": [Action...]                 // run after the roll (and, best effort, if the shot fails)
}
```

Warm-up runs the LOD-ready gate (below) before every take unless `warmup.lod.enabled` is false; then it falls back to
the simple wait: every visible chunk section built and the loaded-chunk count steady for a second, plus `lodSettleSec`.
It never takes less than `minSec` in total. With `scout`, the move is first flown once in real time at `scoutSpeed`. A
gate timeout fails the take with `TIMEOUT` (the gate report in `error.data`) unless `warmup.lod.onTimeout` is
`continue`; previews always continue.

The render result has a `warmup` object (the gate's report) and, with actors, an `actors` array: each actor's final
position, cue states with finish times, and its log (routes, re-routes, breathers, spawn adjustments).

### Targets

| type | fields |
|---|---|
| `point` | `pos`, optional `offset` |
| `player` | `anchor` (`feet`, `center` or `eyes`; default `eyes`), `offset` |
| `actor` | `id` (an actor in this shot or spawned through the API), `anchor`, `offset` |
| `entity` | `uuid` (from `world.findEntities`), `anchor`, `offset` |
| `nearestEntity` | `entityType` (e.g. `minecraft:cow`), `maxDistance` (default 64), `anchor`, `offset`. Locks on to the first match. |

### Moves (`camera`)

Every move takes an optional `shake` of `{amplitudeDeg, frequencyHz}` and an optional `durationSec`. Without
`durationSec`, a move lasts the whole shot, or through the API runs until stopped.

| type | fields |
|---|---|
| `static` | `pos`, then `yaw`+`pitch` or `lookAt` (tracks a moving target; `lookSmoothSec`), `roll`, `fov` |
| `keyframes` | `keyframes[]` (below), `interpolation` (`catmullRom` or `linear`), `easing`, `constantSpeed`, `lookAt` (overrides key angles), `lookSmoothSec`, `fov` |
| `orbit` | `center`, `radius` (`radiusEnd`), `height` (`heightEnd`), `startDeg`, `endDeg`, `easing`, `lookAt` (default the center), `roll`, `fov` (`fovEnd`) |
| `dolly` | `target`, `azimuthDeg`, `elevationDeg`, `distanceStart`, `distanceEnd`, `easing`, `roll`, `fov` (`fovEnd`). Moves along the line of sight. |
| `truck` | `target`, `azimuthDeg`, `elevationDeg`, `distance`, `slideStart`, `slideEnd` (positive is to the camera's right), `track`, `easing`, `roll`, `fov` (`fovEnd`) |
| `follow` | `target`, `offset`, `space` (`world`, or `targetYaw` for `[left, up, forward]`), `smoothSec`, `lookAt`, `lookSmoothSec`, `roll`, `fov` |
| `firstPerson` | `fov` (omit to keep the game's setting). The player's own eyes, for HUD shots and puppet POV. |

A keyframe has `pos`, then either `yaw`+`pitch` or `lookAt` (or neither when the move has `lookAt`), plus optional
`roll`, `fov` and `relativeTo`, a target that `pos` is offset from. Times work one of two ways:

- Every key has `t`, the first `t` is 0, and the last `t` is the duration.
- No key has `t`, and `durationSec` spreads the keys by distance.

Interpolation is Catmull-Rom with the key times as knots, so velocity stays smooth across unevenly spaced keys. Yaw values
are taken as written, so 170 to 190 turns 20 degrees. `easing` is one of `linear`, `easeIn`, `easeOut`, `easeInOut`,
`sineInOut` or `easeInOutQuint`, and remaps time over the whole move. `constantSpeed` re-times the path by arc length.

### Render and preview settings

- `render`: `width`, `height` (even), `fps`, `codec` (`hevc_nvenc`, `h264_nvenc`, `libx264`, `libx265` or `png`),
  `quality` (QP or CRF; lower is better), `tenBit` (HEVC Main10), `serverTickSync`, `sheetFrames` (contact sheet, 0-24),
  and `offscreen` (`auto`, `always` or `never`; see Conventions).
- `preview`: `scale` (0.1-1), `stills` (1-64, first and last frame included), `video` (also write a low-quality video),
  and `fps`.

Batch files (`schema/shots.schema.json`) take the form
`{"version": 1, "render": {...}, "setup": [...], "shots": [...], "teardown": [...]}`.

## Actors and the character director (`schema/actor.schema.json`)

An actor is a client-side `AbstractClientPlayer` with a negative entity id. Only this client sees it, and the server
knows nothing about it. It runs vanilla player physics (gravity, step-up, ladders, snow, collisions) from movement input,
the way a person at a keyboard would. The id `"player"` directs the real local player with the same director instead, as
long as no `skin`, `pos` or `outfit` is given.

```jsonc
{
  "id": "lead",                                // [A-Za-z0-9_-]{1,32}; "player" = the real player
  "skin": {"type": "file", "path": "C:/skins/friend.png", "model": "wide"},   // or {"type": "player"}: the local skin
  "pos": [20937.5, 1791, 7880.5], "yaw": 90, "pitch": 0,   // settled onto the ground once its chunk is loaded
  "outfit": {"suit": true, "hoodStyle": "low_fur/eyes", "hoodDown": false, "mask": false,
             "jacketRgb": 2841796, "pantsRgb": 2841796, "packRgb": 3039144,
             "mainhand": "minecraft:spyglass", "offhand": null},
  "gait": Gait,                                // optional, see below
  "seed": 7,                                   // all noise (meander, glances, breathers); default: hash of the id
  "timeline": [Cue...]
}
```

The outfit uses the Everest Expedition down suit: `hoodStyle` is a look `"shape/goggles"` (0.3.5+: shapes
`expedition`, `parka`, `low`, `low_fur`, `sherpa`, `helmet`; goggles `none`, `hood`, `forehead`, `eyes`, `neck`) or
an old name (`expedition`, `parka`, `forehead`, `goggles_down`); the hood up or down; the oxygen mask. `jacketRgb` and
`pantsRgb` dye the suit (`minecraft:dyed_color`; the hood takes the jacket's colour, boots stay undyed; -1 or absent
is the gold suit with its black hood). The client's `outfit(colourway=...)` sets jacket, pants and pack from the
mod's colourways: red, orange, cobalt, teal, green, violet, black, gold. It also uses Traveler's Backpack's worn pack, dyed `packRgb` (-1 for no pack). Items
take component syntax, e.g. `minecraft:leather_helmet[minecraft:dyed_color={rgb:255}]`. A hook another mod doesn't
accept comes back as a warning, never an error.

### Timelines, cues and triggers

A timeline is a list of cues, each an `action` with an optional `id` and an `at` trigger:

| trigger | fields | fires |
|---|---|---|
| (none) | | at the start |
| `time` | `sec` | seconds after the timeline started (in shots, the take's first frame) |
| `after` | `cue` (own cue id, or `actorId.cueId`), `delaySec` | when that cue finishes |
| `near` | `pos`, `radius` (default 2) | when the actor comes within `radius` blocks (3-D distance) |

All timing counts client ticks since the timeline started. Starting a timeline also restarts walking, looking and their
noise from the seed, so a take plays identically however long the actors stood through the warm-up. Under frame-stepped
capture, re-renders are frame-identical apart from the world itself (mobs, server weather).

| type | fields | finishes |
|---|---|---|
| `walkTo` | `to` or `points`, `speed` (`walk`, `stroll`, `sprint`, `sneak`), `path` (`astar` or `direct`), `arriveRadius`, `maxNodes` | on arrival; fails if stuck after 3 re-routes |
| `lookAt` | `target`, `mode` (`track` or `glance`), `durationSec` | glance: after `durationSec`; track: at once (keeps tracking) |
| `look` | `yaw`, `pitch`, `mode`, `durationSec` | as `lookAt` |
| `lookAhead` | | at once; back to looking ahead with idle glances |
| `face` | `yaw` | at once; the standing body turns there |
| `stop` | | at once; stops walking (the walk cue fails "stopped") |
| `breather` | `durationSec` | after it; an eased stop with a pose cue |
| `jump` | | at once |
| `crouch` | `on` | at once |
| `brace` | `on`, `windYaw` | at once; crouched into the wind, head down |
| `swing` | `hand` | at once |
| `use` | `hand`, `durationSec` (0 = until `release`) | after `durationSec` (draws a held bow) |
| `release` | `arrow` (loose a client-side arrow), `power` | at once |
| `pose` | `hand`, `pose` (`none`, `raise`, `spyglass`, `bow`, `crossbow`, `block`, `brush`), `amount` (`raise` only) | at once; `raise` lifts a radio to the face (below) |
| `equip` | `slot`, `item` | actors only |
| `hood` | `down` | actors only |
| `mask` | `on` | actors only |
| `gravity` | `on` | at once; off holds the walker at its height while it walks (a span its physics won't hold up) |
| `teleport` | `pos`, `yaw` | at once |

#### Raising a radio (`pose: "raise"`)

`raise` keys Everest Radio's raise-to-face animation (`dev.everest8000.radio.client.RadioPose`, reached by reflection).
The arm holding `everest_radio:radio` comes up, main hand first, so equip the radio in `mainhand` or `offhand`; with
neither hand holding one the main arm comes up empty, and the actor log says so. `hand` is ignored. The radio rises in
about 175 ms and lowers in 300 ms, eased in client ticks, so frame-stepped takes repeat exactly. The arm follows the
head, which stays free to look around.

Any other pose, `none` included, lowers it, and so does despawning. `amount` (0-1) pins the height exactly instead of
easing; a later `raise` without `amount` lets go of the pin. `actor.get` reports `radioKeyed` and `radioAmount`. It works
on actor clones and on the real player. Without the radio mod, `raise` falls back to the vanilla horn-to-mouth arm pose
on `hand` and logs a warning, so the mod still works elsewhere.

```python
# The summit call plays at 4 s: the climber raises the radio, and lowers it 3 s later.
actor("caller", pos=..., skin=skin_player(), outfit_spec=outfit(mainhand="everest_radio:radio"),
      timeline=[cue(act_pose("raise"), at_sec=4.0, cue_id="key"),
                cue(act_pose("none"), after="key", delay_sec=3.0)])
```

### Gait: how walking works

```jsonc
{
  "pace": 0.75,                 // forward input at full stride on the flat (1 = vanilla walk)
  "turnRateDegPerSec": 150, "accelSec": 0.6, "lookahead": 2.2,
  "wander": 1.2, "wanderWavelength": 18,        // meander: amplitude (blocks) and blocks per swing
  "uphillSlowdown": 0.45, "snowSlowdown": 0.35,
  "paceAltitude": [{"y": 1200, "factor": 1.0}, {"y": 2000, "factor": 0.58}],   // slower higher up
  "breathers": {"everyMinSec": 22, "everyMaxSec": 40, "minSec": 2.0, "maxSec": 5.0, "slopeFactor": 0.8,
                "altitude": [{"y": 1200, "rate": 0.25}, {"y": 1555, "rate": 1.0}, {"y": 1980, "rate": 1.8}]},
  "idleLook": true
}
```

- **Route.** `walkTo` with `path: "astar"` runs A* over standable blocks. It allows one-block step-ups (with a jump),
  drops of at most 3, and ladders, and never cuts corners. Edges, deep snow, climbing and steep direction-of-travel
  grades cost extra, so on slopes over about 30 degrees the route traverses and switches back instead of going straight
  up. The grid path is then resampled every block and pushed sideways by low-frequency noise (`wander`,
  `wanderWavelength`). Every shaped point is checked against the same walking rules, and the route eases back toward the
  grid path wherever the drift wouldn't fit the ground.
- **Real step heights.** Steps are judged on the real surface heights, partial blocks included: a "one block" step from
  a deep snow layer onto a block topped with more snow can be a 1.5-block climb, which no jump clears. Routes only take
  climbs up to 1.12 blocks.
- **Steering.** Pure pursuit on that route, with a turn-rate limit and acceleration and deceleration. The actor checks it
  can actually walk to the pursuit point before committing to it. If it makes no progress for 5 s, or has jumped three
  times at the same spot for 1.5 s, it walks back onto the route, and if that fails it routes again.
- **Pace.** `pace` scaled by uphill grade, snow depth and the `paceAltitude` curve, smoothed, a little faster on the
  flat and slower on step-ups.
- **Breathers.** Effort builds while walking at a rate set by the `altitude` curve times `1 + slopeFactor x grade`. When
  it passes a randomised threshold between `everyMinSec` and `everyMaxSec`, the actor eases to a stop over 0.6 s and
  holds for `minSec`-`maxSec` (randomised). Then it eases back up over 0.6 s. So stops are rare low down and come every
  20-40 s of effort high up. Each breather plays one of three pose cues: head down at the feet then up at the slope
  ahead, a look back at the nearest other actor (or down the route), or a slight crouch with the head down. Omit
  `breathers` for none.
- **Look.** The head leads and the body follows. The head turns with a damped, speed-limited motion and never more than
  70 degrees from the body, and a standing body turns to follow a head held far to one side. With no target there are
  occasional idle glances, wider while standing.

`client/cinema.py` has `everest_gait()`, the Mt. Everest 8000 climber tuned on the map's heights. The offline demo below
charts it.

## LOD-ready gate (`schema/lodGate.schema.json`)

Before every take (and on demand through `world.awaitLodReady`) the gate waits until the world is drawn in full, with
**Distant Horizons' own progress as the signal** rather than a timer. After a teleport DH can take minutes to stream
detailed LODs from the server, and only its status knows when it has finished.

What the gate reads (`world.lodStatus`, from DH 3.3.3's internals by reflection; the names come from the jar):

| field | what it counts |
|---|---|
| `executors` | queued and running tasks on DH's pools: world gen/import, render load, file handler, update propagator, LOD builder, networking (the data behind its F3 lines) |
| `retrieval` | the LOD retrieval queue: waiting, in progress, estimated chunks remaining (generation, or requests to the server in multiplayer) |
| `network` | the full-data request queues to the server: waiting, in progress |
| `renderTasksQueued` | tasks queued for the render thread (GPU uploads) |
| `quadtree.sectionsBuilding` | enabled render sections still building, uploading or dirty |
| `quadtree.sectionsCoarse` | enabled sections drawn coarser than the detail level the quadtree wants at their distance |
| `quadtree.missingPositions`, `queuedPositions`, `sectionsToReload` | positions with no data yet, queued for retrieval, or queued to reload |
| `activity` | everything in flight (all of the above except missing and coarse) |
| `outstanding` | still to come: missing positions plus coarse sections |

1. **Warm pass** (`warm`): the camera, with the rider when the shot rides, visits points along the take's path (every
   `warmSpacing` blocks, at most `warmMaxPoints`). At each it waits until DH has been idle for `warmQuietSec` (at most
   `warmPointMaxSec`), so detail along a long move is requested before the take, not during it.
2. **Settle** at the first frame's pose until all of these hold, and at least `minSec`:
   - `activity` has been 0 for `quietSec`;
   - `outstanding` is 0, or has not changed for `stallSec` while DH is idle. Past the edge of a pre-generated map there
     is no data to get, so those positions never fill;
   - every visible chunk section is built and the loaded-chunk count is steady;
   - with `frameStability` (a cross-check), the mean change in block-averaged brightness between rendered frames has
     stayed under `frameThreshold` (0-255) for `frameQuietSec`.

After `timeoutSec` (default 5 min, warm pass included) the gate ends with `"timeout"`. A shot then fails with `TIMEOUT`,
and `world.awaitLodReady` raises it, unless `onTimeout` is `continue`. Either way the report is complete: `elapsedSec`,
`warmSec`, `settleSec`, `dhIdleAfterSec` (when the final idle run began), the warm-pass log, the final DH status with
its F3 lines, the chunk and frame readings, and a `timeline` with one row a second (`t`, phase, activity, outstanding,
missing, coarse, building, network, retrieval, render tasks, executors, frame diff). Every render keeps this under
`warmup`, so the real waiting times are on record.

With `stills`, the gate writes `<shot>_gate_start.png` (on arriving at the start pose) and `<shot>_gate_done.png` (the
frame it judged ready) next to the video, to confirm by eye that "done" means detailed.

Defaults: `quietSec` 5, `stallSec` 10, `minSec` 3, `timeoutSec` 300, `onTimeout` `fail`, `warmSpacing` 160,
`warmPointMaxSec` 60, `warmMaxPoints` 10, `warmQuietSec` 2, `frameThreshold` 0.6, `frameQuietSec` 3.

Streaming speed is set on the server: DH's `[server] playerBandwidthLimit` / `globalBandwidthLimit` (KB/s; 0 = no
limit) can be changed live by an operator with `/dh config common.playerBandwidthLimit <KB/s>` and
`/dh config common.globalBandwidthLimit <KB/s>`.

## API reference (JSON-RPC 2.0)

Each message is one JSON object per line over TCP to `127.0.0.1:<port>`, UTF-8 and `\n`-terminated. Parameters go by
name, unknown parameters are rejected, and batches are not supported. Calls on one connection run in order, so open a
second connection to poll status while a long call runs.

If a token is configured, every connection must first call `session.hello {token}`. It returns `apiVersion`, the mod
version and the list of methods.

Read-only calls work at any time. Calls that change state return `BUSY` while a `capture.render` or `capture.start` is
running.

### Errors

| code | name | meaning |
|---|---|---|
| -32700 / -32600 / -32601 | parse error, invalid request, method not found | malformed JSON-RPC |
| -32602 | INVALID_PARAMS | `data: {path, reason}`, e.g. `params.shot.camera.keyframes[2].pos: expected [x, y, z]` |
| -32603 | INTERNAL | `data: {exception, message}` |
| -32000 | NOT_IN_WORLD | title screen, connecting or disconnected |
| -32001 | UNAUTHORIZED | missing or wrong token |
| -32002 | BUSY | a render or capture is running |
| -32003 | TIMEOUT | a wait ran out (teleport arrival, shader reload, an actor timeline, ...); `data` holds the actor state where relevant |
| -32004 | COMMAND_FAILED | the server answered in red; `data` holds the feedback |
| -32005 | CAPTURE_FAILED | ffmpeg missing or crashed; `data.log` holds the end of its output |
| -32006 | NO_SNAPSHOT | `state.restore` before `state.snapshot` |
| -32007 | CANCELLED | replaced, stopped, cancelled, despawned or disconnected |
| -32008 | UNSUPPORTED | for example shaders without Iris, or riding outside spectator mode |
| -32009 | NOT_FOUND | a target entity or actor isn't there, or a skin file can't be read |
| -32010 | STUCK | a walk was blocked for 5 s (puppet), or an actor walk failed after re-routing |

## Examples

Orbit a summit (`examples/orbit_summit.json`), a batch file with one shot:

```json
{"version": 1, "render": {"width": 2560, "height": 1440, "fps": 60, "codec": "hevc_nvenc", "quality": 16},
 "shots": [{"name": "summit_orbit", "durationSec": 8,
   "camera": {"type": "orbit", "center": {"type": "point", "pos": [20706.5, 2032, 7774.5]},
              "radius": 170, "height": 30, "startDeg": 250, "endDeg": 285, "fov": 50, "easing": "sineInOut"},
   "player": {"visible": false, "ride": true},
   "setup": [{"type": "time", "dayTime": 12250}, {"type": "command", "command": "weather clear"}]}]}
```

A fly-through (`examples/flythrough.json`): Catmull-Rom keyframes that look at a fixed point and fly by arc length at
constant speed, with a scouting pass first so chunks and LODs along the path are loaded.

A walking-player tracking shot (`examples/walk_tracking.py`): the puppeted player walks a ridge while a `follow` camera
(`space: "targetYaw"`, smoothed) rides behind and to the side.

Three climbers on the summit ridge (`examples/team_on_the_ridge.py`, which also writes `team_on_the_ridge.json`). Three
actors with two skins and different hoods, masks and pack colours start a few blocks apart above the South Col and climb
with `everest_gait()`. The middle climber glances back at the third at 5.5 s, and the lead takes a breather at a marked
spot. The camera trucks alongside the middle climber:

```python
team = [
    actor("lead", pos=(20937.5, 1791, 7880.5), yaw=90, skin=skin_player(),
          outfit_spec=outfit(hood_style="goggles_down"), gait_spec=everest_gait(), seed=7,
          timeline=[cue(act_walk_to((20869.5, 1853, 7880.5)), cue_id="climb"),
                    cue(act_breather(4.0), near=(20905.5, 1819, 7880.5), radius=2.5)]),
    actor("second", pos=(20943.5, 1786, 7880.5), yaw=90, skin=skin_file(FRIEND_SKIN),
          outfit_spec=outfit(pack_rgb=0x2E5FA8), gait_spec=everest_gait(), seed=99,
          timeline=[cue(act_walk_to((20875.5, 1847, 7880.5))),
                    cue(act_look_at(actor_target("third"), mode="glance", duration_sec=1.8), at_sec=5.5)]),
    actor("third", ...),
]
s = shot("team_on_the_ridge", 10,
         truck(actor_target("second", anchor="center"), azimuth_deg=0, distance=14, slide_start=3, slide_end=-3,
               elevation_deg=8, track=True, easing="sineInOut", fov=40),
         player={"visible": False, "ride": True}, actors=team, warmup={"lod": lod_gate(min_sec=8)})
```

## Tools

- `tools/render_shots.sh` / `render_shots.py`: the headless batch runner (above). `--validate-only` checks a file
  without the game.
- `tools/sky_check.py`: the sky-flicker regression check. `analyze <video>...` measures the tick-locked (20 Hz at 60 fps)
  pulse in the sky band of any render and fails above `--max-pulse` (1.5). `run` renders a fast riding flight and a
  static riding shot through the API (1280x720; a few minutes with the LOD gate), analyses both, and also fails on server
  position corrections during the roll. Old riding renders measure 5.8 (khumbu flight) and 11.4 (Western Cwm flight);
  non-riding renders 0.5-0.8.
- **Offline director demo**: `gradle test` drives the locomotion and look code on a real heightfield. That's the South
  Col climb, 157x762 blocks exported from the map (`src/test/resources/terrain_southcol.bin`), with a toy body that
  slides along walls. The tests check that routes go around cliffs, step up one block but not two, and climb ladders,
  and that the ridge walk arrives without getting stuck and plays the same twice. The demo writes charts to `build/demo/`:
  `director_vs_puppet_map.png` (routes), `director_vs_puppet_series.png` (forward input, turn and look over time) and
  `two_actors_two_seeds.png` (two seeds on the same route, with a zoom on one breather).

## Notes

- **Placing the camera.** The camera can go anywhere, but full-detail chunks exist only near the player, and Distant
  Horizons covers the rest. With `player.ride` the hidden spectator player travels with the camera. Actors far from
  the player stand still until their chunk loads (entities in unloaded chunks don't tick), so ride or teleport near
  them.
- **Actors are client-side.** Other players and the server don't see them, they can't trigger server mechanics
  (pressure plates, mobs targeting them, server-side wind or freezing), and server-only effects on the real player
  don't apply to them. Client-side visuals keyed to a player entity, such as the Expedition hood and mask, do apply.
- **What renders.** The player model renders because the camera is detached. The mod suppresses the player's own name
  tag, block outline and hand while the cinema camera is active, and actors never show name tags. Chat and crosshair
  can be hidden separately from the rest of the HUD.
- **Input.** The mouse can't turn the player while the mod is enabled. The puppet's or the `"player"` actor's movement
  replaces keyboard movement while it's engaged.
- **Restoring state.** `state.restore` can't see mod-specific inventories, such as a backpack slot added by a mod. Back
  up the player file around a batch if that matters; the Everest wrapper does.
